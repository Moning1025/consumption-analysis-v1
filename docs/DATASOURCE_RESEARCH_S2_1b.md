## 0. 结论摘要（先看这三行）

1. **省级月度社零拿得到，而且零门槛、不要 Token**：四川省统计局、四川省商务厅都以**网页 HTML 表格 + 附件（ZIP/XLS）**的形式按月公开，实测 HTTP 200，字段名已抄下来。

## 3. 问题一：怎么调 API？需不需要 Token/AppKey？

这要**分两类**回答，因为这两类根本不是一回事：

### 3.1 统计局 / 商务厅：不是 API，是"网页 + 附件"，不需要任何 Key

【已核实】这两家的"数据发布"栏目就是普通政务网页：

- 每期一篇文章，正文里是一张 HTML `<table>`，直接 `requests.get()` + 正则/`pandas.read_html()` 就能拿到；
- 部分文章正文只放图，真数据在**附件**里（四川省统计局是 `.zip`，商务厅是 `.xls`）；
- 没有任何鉴权、没有 `appkey`、没有 `token`。

**代价**：要自己写"列表页翻页 → 文章 URL → 解析表格 → 下载附件"的流程，而且**页面结构改版就会坏**（这也是我为什么要在 S2-1b 里做"解析失败要报错、不许静默返回空表"）。

### 3.2 开放平台（成都 / 四川）：是 API，需要注册 + 实名 + 申请授权

【未核实，需登录确认】从页面结构看，它们属于"开放数林"那一类平台，标准流程是：

1. 注册账号 → **实名认证**（个人一般要身份证/人脸，部分平台学生认证可用）；
2. 在"数据服务 / 接口"里找到目标接口 → 点"申请"；
3. 审批通过后，在"开发者中心 / 我的应用"里拿到 **AppKey**（有的叫 `appkey` / `appKey` / `clientId`，并配 `secret`）；
4. 调用时把 key 放在 **请求头**（常见 `Authorization` 或 `appkey`）或 **查询参数** 里；有的还要求签名 `sign`（把参数按字典序拼 + secret 做 MD5/SHA）。

**准确参数名、签名算法、限流数值，必须登录后从"接口详情 → 调用示例"里抄**——这部分我拿不到，不编。

**判断**：走开放平台 = 多一道审批（可能 1–3 个工作日），换来"结构化 JSON + 稳定接口"。走统计局网页 = 零审批，但要多写解析、要防改版。

## 4. 问题二：字段名到底叫什么？有没有住宿餐饮细分？

### 4.1 【已核实】四川省统计局月度表（这是最值钱的样本）

URL 示例：`https://tjj.sc.gov.cn/scstjj/c111996c/2026/2/3/cb0127bd1a1b4fcc80037d233590fd5f.shtml`（社会消费品零售总额 2025年12月）

表头**逐字**是这五列：

```
指标名称 | 本月 | 本月±% | 本月止累计 | 累计±%
```

行结构（逐字）：

```
社会消费品零售总额(亿元)     2739.7   1.9   29135.4   5.1
一、按经营地分
（一）城镇                  2203.9   0.7   23582.1   4.9
（二）乡村                   535.8   6.9    5553.2   6.1
二、按消费形态分
（一）餐饮收入               412.7   3.6    4026.7   3.7
（二）商品零售              2327.0   1.5   25108.7   5.4
```

每篇还提供附件下载（`.zip`，内含完整表）。

### 4.2 【已核实】四川省商务厅月报

URL 示例：`https://swt.sc.gov.cn/sccom/gnmy/2026/10/23/51fe9ccfa94b42fb8338a4e7c3d41dd2.shtml`
标题：《全省社会消费品零售总额结构表(2026年1-9月)》，表头是：

```
指标名称 | 累计 | 同比±%
```

行：社会消费品零售总额、按经营地分 城镇 / 乡村；附件 `.xls`。发布节奏很规律——**每月 23 日左右发上月累计**（1-2、1-3 … 1-12）。

### 4.3 关于"住宿餐饮细分"——**关键澄清**

社零这个指标体系里，**按消费形态只分两项：餐饮收入 / 商品零售**，"住宿"不单列（住宿业营业额属于"服务业营业额"口径，不在社零里）。

所以老大要的"住宿餐饮细分"，在社零口径下**只能拿到"餐饮收入"这一项**，拿不到"住宿"。要住宿数据得换指标（比如"限额以上住宿业营业额"），那是另一个数据源，S2-1b 不建议碰。

**答辩时这句话可以直接用**：「社零按消费形态只分餐饮收入和商品零售两类，住宿不在社零口径内；我没有硬凑一个不存在的字段。」

### 4.4 区（市）县级

【未核实 / 风险项】公开网页上我**没有**找到稳定的"区县级月度社零"。已知存在的位置是：

- 成都市统计年鉴（年度，含分区（市）县主要指标表）——但 `cdstats.chengdu.gov.cn` 现在直连 412，需要浏览器或换入口；
- 各区（市）县自己的《国民经济和社会发展统计公报》（年度，单个区县一篇）；
- 成都公共数据开放平台上可能有"区（市）县社零"数据集（需登录搜索确认）。

→ 这直接决定第 6 节选哪个方案。

## 6. 三个方案与取舍（老大拍板用）

### 方案 A：只做"省级月度"，砍掉区县级（**推荐先做这个，1–2 天**）

- 数据：四川省统计局月度表（省级、月度、5 个指标 × 12 个月）+ 商务厅月报做交叉校验（两家数字应当一致，不一致就说明我解析错了——这是天然的验证）。
- 优点：零审批、今天就能跑、字段名已实测、证据链最干净（政务公开页面 + 我留 URL 和抓取时间）。
- 缺点：**没有区县维度**，蓝海/红海那张图的"需求侧"只能到市州级或全省级。
- 对答辩的影响：地图上"某区火锅密度高但消费密度低"这个卖点做不出来；但"多源融合 + 时间序列 + 真实数据"仍然成立。

### 方案 B：A + 成都开放平台拿区县级（**要老大花半天做审批**）

- 老大需要做的事（约 30 分钟）：注册 → 实名认证 → 搜"社会消费品零售总额" → 看有没有区县级 → 申请 → 拿 AppKey。
- 如果有区县级月度：完美，S2-1b 按原计划走。
- 如果只有**年度**区县级：`region_consumption_monthly` 的 `period` 存 `2025`（年度），加字段 `period_kind='year'`，答辩口径改成"月度供给 + 年度需求"，并解释为什么（区县月度社零不公开）。
- 如果没有：走方案 C。

### 方案 C：区县级改用"年度 + 统计年鉴/区县公报"（**兜底，2–3 天**）

- 每年一篇，覆盖成都 20 个区（市）县，字段同 §4.1；来源是各区县统计公报。
- 代价：要写 20 个不同站点/不同版式的解析器，**工作量不可控**，且容易改版就坏。
- 我的建议：**不做 20 个站点**。只在成都统计年鉴（一个源）里把分区县表抠出来，一个解析器解决。

**我的推荐顺序：A 今天做 → 同时让老大去做 B 的注册（并行，不占我工时）→ B 不成立再考虑 C。**

## 7. 表结构建议（按实测字段名改 `region_consumption_monthly`）

统计局这张表有个坑：**同一期同时给"本月"和"本月止累计"两个口径**，如果用 `(indicator, region, period)` 做主键，会把两个口径挤在一行、或者互相覆盖。所以必须加 `period_kind`：

```sql
CREATE TABLE IF NOT EXISTS region_consumption_monthly (
    indicator_code  TEXT NOT NULL,   -- social_retail_total / retail_goods / catering_revenue / urban / rural
    region_code     TEXT NOT NULL,   -- 510000（省）/ 510100（市）/ 510107（区县）
    period          TEXT NOT NULL,   -- '2025-12'（月度）或 '2025'（年度）
    period_kind     TEXT NOT NULL,   -- 'month'（本月）/ 'cumulative'（本月止累计）/ 'year'
    granularity     TEXT NOT NULL,   -- nation / province / city / district
    region_name     TEXT,
    value           REAL,            -- 本期值
    yoy_pct         REAL,            -- 本期同比±%
    unit            TEXT,            -- 亿元
    source          TEXT,            -- sc_stats / sc_commerce / chengdu_opendata
    source_url      TEXT,            -- 证据链：原始页面
    raw_json        TEXT,            -- 原始行快照，便于追溯
    fetched_at      TEXT,
    PRIMARY KEY (indicator_code, region_code, period, period_kind)
);
```

**为什么这么设计（答辩可讲）**：主键里带 `period_kind`，是因为"本月"和"累计"是两个独立事实，不是同一个数的两种写法；混在一个字段里会导致 `INSERT OR REPLACE` 静默覆盖，数据就对不上了。

## 9. 失败回退

1. **抓统计局返回 412 或空表** → 说明触发了 JS 挑战或页面改版：先 `print(response.status_code)` 和 `len(response.text)`；为 0 或 412 就不要继续解析，直接报错退出并记 `source_url`，**不许写入空数据**。
2. **解析出 0 行** → 先存原始 HTML 到 `docs/_tmp/` 再对比选择器；十有八九是表格列数变了（多一列"备注"就会整体错位）。
3. **两家数字对不上**（统计局 vs 商务厅）→ 大概率是"累计口径 vs 当期口径"混了，检查 `period_kind`；其次检查单位（亿元 vs 万元）。
4. **开放平台返回 401/403** → 依次查：Key 是否过期、IP 白名单、调用频次超限、签名算法（参数是否按字典序、是否含 `sign` 字段本身）。

## 12. 五维口径补充与"商业数据"的替代方案（2026-11-12 追加）

### 12.1 系统口径升级：三源 → 五维

老大当天把系统定位从"空间 + 流水"扩为 **"空间 + 人口 + 灯光 + 流水 + 宏观"五维融合**，本报告负责的是其中**宏观**这一维，其余四维的分工：

| 维度 | 数据源 | 落到哪 | 作用 |
|---|---|---|---|
| 空间（供给） | 高德 POI（S2-1a） | `poi_merchant` | 商家在哪、卖什么、评分/人均多少 |
| 人口（分母） | WorldPop 100m 栅格（S2-1d） | `spatial_grid.pop_total` | "每万人有多少家同类店" |
| 灯光（活力） | NPP-VIIRS 年均（S2-1d） | `spatial_grid.night_light` | 同样店数在更亮的地方含义更重 |
| 流水（行为） | Olist（S2-1c） | `consumption_record` | 客群 RFM、真实脏数据 |
| 宏观（标尺） | 省统计局 / 商务厅（本报告） | `region_consumption_monthly` | 趋势与季节的锚点，校验局部 |

> 一句话口径：**宏观是标尺，不是主力**——用标尺校准局部，而不是拿局部冒充全局。

### 12.2 大众点评 / 美团：明确放弃，理由要背下来

| 为什么放弃 | 具体说明 |
|---|---|
| 合规 | 抓取违反平台用户协议；数据不可二次分发、不可写进公开发布的论文数据集 |
| 稳定性 | 反爬强度高、验证码/滑块频繁，工期不可控（毕设最怕"演示前一天挂了"） |
| 可讲性 | 答辩被问"你这数据合法吗"，答不上来就是硬伤；而官方/公开数据源可以当场给 URL |

### 12.3 替代方案：用高德 POI 的 `biz_ext` 做"消费质量"代理

高德 `/v3/place/text` 在 `extensions=all` 时，每条 POI 带 `biz_ext` 字段，其中：
- `rating`：商户评分（字符串，如 `"4.7"`）
- `cost`：人均消费（字符串，如 `"88.00"`，单位元）

**实测覆盖率（本地真实库 `poi_merchant`，100 条样本，2026-11-12）**：

| 检查项 | 结果 |
|---|---|
| `raw_json` 中含 `biz_ext` | **100 / 100** |
| `rating` 非空 | **100 / 100**（4.7 – 4.8） |
| `cost` 非空 | **100 / 100**（73.00 – 115.00 元） |
| 样本构成 | 以餐饮为主（火锅/咖啡等关键词采集） |

**能支撑什么**：
- 消费质量维度：同品类里"人均 115 元"与"人均 73 元"的店，客群档次不同，不能等权看待；
- 蓝海算法的加权：需求侧（人口/灯光）× 质量权重（rating/cost）→ 比单纯数店铺更接近"赚钱"这个目标。

**不能支撑什么（必须诚实写在论文里）**：
- 不是真实交易流水，是**平台挂牌价与评分**，存在商家自填/刷分噪声；
- 餐饮以外品类（尤其零售）`cost` 覆盖率显著下降——**完整分品类覆盖率统计留到 S3 清洗阶段作为一条数据质量指标输出**，不要现在拍脑袋给数字。

### 12.4 答辩口径（新增，配合 §10）

- **问法**：「商业平台的数据（大众点评、美团）你为什么不抓？那你怎么知道消费能力强弱？」
- **一句话答案**：「抓商业平台违反它们的协议、数据也不能二次分发，毕设没必要冒这个合规风险。消费质量我改用高德 POI 自带的 `rating` 和 `cost`——本地 100 条实测这两项覆盖率都是 100/100，可复现、可溯源。」
- **追问**：「评分和人均准吗？」→「不准到能当账本，但够用来做**相对排序**；而且我在清洗阶段会输出分品类的覆盖率与缺失率，缺失多的品类会降权处理，不硬凑。」
