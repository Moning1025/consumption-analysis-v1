## 阶段 S0 · 工程基线（Git 与目录治理）

### 问题 1 · 仓库里混进了构建产物与数据库文件

- **我遇到的难题**：项目已推到 GitHub，但仓库里有 45 个不该进版本库的文件（27 个 `__pycache__/*.pyc`、数据库文件 `local_consumption_insight.db`、17 个 `store/unpacked/` 下的样例解包文件）。我不知道怎么把它们"从仓库里删掉但保留在本地"，还怕一操作就把代码删了。
- **AI 给的思路**：区分"工作区文件"和"版本库跟踪记录"两个概念——用 `git rm -r --cached` 只摘掉跟踪记录、不动磁盘文件；先写好 `.gitignore` 再摘，否则下次 `git add` 又会被加回来；摘除后单独一次提交，并给出"提交前先 `git status` 确认只有 D 在暂存区"的检查步骤。
- **我做的决策**：采纳全流程，但**否决了 AI 顺手清理 `store/unpacked/` 实体的建议**——那是历史解包样例，答辩时可能要用作"多格式接入"的证据，只排除出版本库、不删磁盘。同时我要求把 `.db`、`.env`、`docs/_tmp/` 一起写进忽略规则，因为我知道后面要接 API Key。
- **最终结果**：`.gitignore` 重写；`git rm -r --cached` 摘掉 45 个文件；提交 `ea55245`（45 files changed, 901 insertions, 144 deletions）。之后 `git status` 干净，本地 HEAD 与远端 `master` 一致。

### 问题 2 · 推送失败，分不清是网络问题还是权限问题

- **我遇到的难题**：`git push` 报 `fatal error - couldn't create signal pipe, Win32 error 5`，但 `ssh -T git@github.com` 又是成功的（`Hi Moning1025`）。我完全不知道该修哪一边。另外仓库里有两个 remote，其中一个是我拼错的 `origih`，指向一个加速地址。
- **AI 给的思路**：`ssh -T` 通说明密钥与 GitHub 侧权限没问题，报错发生在 Git 调 `sh.exe` 建管道的环节，属于执行环境限制而不是仓库配置问题；建议先用 `git ls-remote` 判断是"读"就失败还是"写"才失败，再决定是否换执行方式。同时指出拼错的 remote 是个隐患，建议删掉只留一个。
- **我做的决策**：采纳诊断路径；删除拼错的 `origih`，只留 SSH 的 `origin`；接受"推送这类写操作要在有完整权限的终端里做"这一结论，并给自己定了一条规矩：**以后任何 push 之前先确认要推什么内容**。
- **最终结果**：`origin` 唯一且为 SSH；推送成功，远端更新到 `5513419`；养成 `git status` + `git log --oneline -10` 的提交前检查习惯。

## 阶段 S1 · 异步任务链路（长任务不冻结窗口）

### 问题 1 · 长任务冻结窗口，进度条是假的

- **我遇到的难题**：点"开始分析"之后整个窗口卡死几十秒，动都动不了；进度条却在匀速走——我后来才发现那个进度是 `bridge_api.py` 里 `sleep` + 按时间推算出来的，跟后台真实做了什么毫无关系。答辩如果被问"进度条是真的吗"，我按现状是答不出来的。
- **AI 给的思路**：把"提交任务"和"执行任务"拆开——提交即刻返回一个 `job_id`，真正干活放到后台线程池；真实状态落在两张表里：`job_run`（一行，快照：状态/阶段/进度/消息）和 `job_event`（多行，日志，按 `seq` 递增）。前端只轮询 `job_run` 的一行 + 增量拉 `job_event`，**进度只能由任务自己上报**，不许前端推算。取消做成协作式：前端只置 `cancel_requested=1`，任务在阶段边界自查后退出，不强杀线程。
- **我做的决策**：全盘采纳，但追加了三条自己的约束：① 所有写操作必须是短事务（我查过 SQLite 是单写者，长事务会把前端轮询堵死）；② 先写断言脚本 `scripts/verify_job_store.py` 再改 `main.py`，不能"凭感觉能跑"；③ 上线前必须先删掉 `main.py` 里那段"启动时把任务强制置为已完成 100%"的假数据逻辑，否则新链路永远显示假的完成态。
- **最终结果**：`schema_v2.sql` 新增 `job_run` / `job_event`；`store/job_store.py` 12 个函数全部通过 `verify_job_store.py` 的 29 项断言（29/29 PASS）；真实库升级后 15 张表，`job_run`/`job_event` 各 0 行（干净起点）；`main.py` 的伪造逻辑已删除；前端 `web/index.html` 用 700 ms 轮询 `get_job`，日志按 `seq` 增量追加，任务面板显示阶段/进度/ETA/日志。

## 阶段 S2-1 · 环境盘点与测法争议（本周进行中）

### 问题 1 · 不清楚本机 Python / JDK / MySQL 状态，怕规划落空

- **我遇到的难题**：写路线图时完全靠猜——不知道本机到底装了哪些包、有没有 JDK、MySQL 在不在、D 盘还剩多少。如果按"理想环境"排计划，做到 S5 才发现没有 MySQL，整条线就崩了。而且 `pip list` 在我机器上会卡死两分钟以上。
- **AI 给的思路**：先做一次**只读**环境扫描（禁止安装、禁止写文件、禁止开窗口），输出结构化报告；把"确定的版本号 / 确定没有的东西 / 硬件余量"写成事实基线存进备忘文档，后续所有选型都引用这份基线而不是凭印象。`pip list` 卡住就改用 `importlib.metadata.version(包名)` 逐个问，秒回。
- **我做的决策**：采纳，并要求把"没有的东西"也写清楚（比如 `pyarrow`、`duckdb`、`pymysql`、`pyspark` 全都没有），因为这直接决定 S3 能不能落 Parquet、S5 要不要装驱动。另外我补充了资源约束：内存 15.7 GB 但可用只有 2.8 GB、D 盘剩 47.9 GB、CPU 是 16 物理核 / 24 线程的大小核异构——这三条决定了 Spark 阶段不能用 `local[*]`。
- **最终结果**：环境基线落进 `docs/PROJECT_MEMO.md`（解释器路径、JDK 21 位置、MySQL 服务名与状态、四个大数据环境变量全空、硬件数字）；据此把路线图里"S5 需装 MySQL"改成"MySQL 已装只需启动服务"，把 S7 的 JDK 从 17 改成已存在的 21，并在 S7 写了 `local[8]` + `driver.memory=2g` 的硬性应对。

### 问题 2 · Pandas 比纯 Python 循环慢 5 倍，我以为实验做废了

- **我遇到的难题**：为了答辩准备"清洗为什么用 Pandas"这道题，我造了 10 万行真实字段结构的数据做对比。结果循环版 7.71 ms、Pandas 版 41.73 ms，**Pandas 慢 5.4 倍**。这跟"Pandas 快一个数量级"的常识完全相反，我第一反应是实验写错了，但又找不到错在哪。
- **AI 给的思路**：先别改结论，先查测法——Pandas 这一段实际包含两件事：把 10 万个 dict 变成 DataFrame（建表），和 groupby 聚合。建表要逐行读键、推断类型、分配列内存，很可能占了绝大部分；建议把两段拆开分别计时，并且**表必须在计时循环外只建一次**，否则重建的内存分配会污染聚合的读数。同时提醒：只比速度不比正确性等于比了个错东西，分阶段那一路的聚合结果也必须和循环版做一致性校验。
- **我做的决策**：要求 AI 先证明"② 聚合里不含建表开销"再下任何结论，具体三条：① 贴出完整代码我核对计时边界；② 分阶段结果必须进 `_check_same` 校验；③ "聚合结果一致：True/False" 必须和倍率同一屏可见。**否决了直接改结论写成"Pandas 更快"的做法**——那等于为了好看造假。
- **最终结果**：`scripts/exp_pandas_vs_loop.py` 改为两轮独立计时（建表单独一轮；聚合在循环外建好的表上重复跑），并新增 `_check_same` 校验与同屏一致性输出。**最终实测（10 万行、三轮取中位数）**：循环版 7.58 ms；Pandas 整体 40.05 ms，拆开是建表 37.72 ms + 聚合 3.10 ms；只比聚合时循环版仅快 2.4 倍（不是数量级），「聚合结果一致：True」。我自己动手改了两处 `agg` 写法（`agg("sum")` 与 `agg({"consumption_amount": "sum"})`），其间撞上 Pandas 2.x 的 nested renamer 报错，借此弄清三种 `agg` 写法的返回结构不同（Series 与 DataFrame 的区别，要看 `.to_dict()` 之前拿到的是谁）。另外把品类从 5 个改成 6 个重跑，耗时几乎没变化——说明 groupby 的耗时只跟行数走、跟类目数基本无关，这条是论文「系统测试」章最硬的一条数据。结论从"快 N 倍"改成有边界的版本：数据已在内存的小规模聚合，dict 循环更快；Pandas 赢在"表建一次、反复做多指标聚合"和"从文件/SQL 列式读入"。这条边界比一个虚高的倍数更适合答辩——它证明我知道工具在哪里快、在哪里慢。

## 阶段 S2-1a · 高德 POI 接入（2026-11-12 完成）

### 问题 1 · 采回来的数据，我凭什么证明是真的

- **我遇到的难题**：跑通之后库里躺着 50 条商户，字段齐全、经纬度也在成都。但答辩时老师只要问一句"这些是接口返回的，还是你自己 `INSERT` 进去的"，我就答不上来——因为表里只有结果，没有过程。这跟 S1 那个"假进度条"是同一个毛病：**只有结论，没有证据**。
- **AI 给的思路**：把"采一次"当成一次**记账**——每发一个请求就写一行 `poi_fetch_log`（第几页、返回几条、新增/覆盖/跳过各几条、耗时、错误码），最后校验 `返回 = 新增 + 覆盖 + 跳过`，差一条都不许通过。这个式子在任何一次跑批里都必须成立，成立就说明解析和写库两头都没吞数据。
- **我做的决策**：采纳，并且追加三条自己的规矩：① 这个等式要写进 `verify_s2_1a.py` 当验收项，不能只靠我肉眼看打印；② `--dry-run`（不写库）必须**跳过**守恒核对，否则会误报"不守恒"；③ 我发现最初那版打印是个恒真表达式（`返回 == 新增 + 覆盖 + 跳过` 写成了直接打印变量），等于没校验，要求改成真判断。另外要求原始响应整条存进 `raw_json`，出问题时能拿原始 JSON 对账。
- **最终结果**：真实 Key 实跑 `--city 成都 --keywords 火锅,咖啡 --pages 2` → 4 次请求、**返回 100 = 新增 100 + 覆盖 0 + 跳过 0，差 0**，4 条账本记录；`verify_s2_1a.py` **8/8 项 PASS**（行数、`poi_id` 唯一、经纬度非空 100%、中国 bbox、四川 bbox、adcode 覆盖 100%、adcode 前缀 51、账本守恒）。分布：餐饮服务 97 / 购物服务 1 / 生活服务 1 / 汽车销售 1；武侯 60 / 锦江 20 / 成华 7 / 青羊 6 / 双流 4。

### 问题 2 · `self.retry_base` 写在 `__init__` 外面，直接 NameError

- **我遇到的难题**：改重试逻辑时，我把 `self.retry_base = 1.0` 写到了 `__init__` 方法的外面（写到类体里去了），运行直接 `NameError: name 'self' is not defined`。我一开始以为是导入顺序问题，看了半天没看出来。
- **AI 给的思路**：`self` 只在**方法内部**存在，类体里没有 `self` 这个东西；类体里能写的是普通属性（`retry_base = 1.0`，属于类、所有实例共享），要实例自己的就用 `__init__` 里 `self.retry_base = 1.0`。两种情况都合法，但含义不同：写在类体里、之后在方法里又用 `self.retry_base += 1` 去改，会**凭空创建实例属性**，类属性不变——这类 bug 不会报错，只会让"重试三次"变成"每次都从 1 秒开始"。
- **我做的决策**：自己动手修——把赋值移进 `__init__`，并确认后面所有读写都走 `self.`。同时定了一条：**凡是带状态的重试参数，一律进 `__init__`**，避免"看起来改了其实没改"。
- **最终结果**：NameError 消除，实跑 4 次请求 **0 次重试**（没有触发限流，说明 `min_interval=0.35` 的节流够用）；退避策略当前是固定 1 秒，指数退避的改造留给下一步按需切换。

## 阶段 S2-1b · 宏观消费数据接入（2026-11-15，年鉴导入版完成）

### 问题 1 · 原计划的"开放平台 API"，实测走不通

- **我遇到的难题**：设计里写的是"成都公共数据开放平台拿区县级社零"。真去调才发现：成都侧直连返回 **HTTP 412**（瑞数 JS 挑战，正常请求直接被拦）；四川开放平台列表页能打开、详情页未登录是空白；`data.stats.gov.cn` 直接 **403 UrlACL**（出口 IP 被拦）。三条路堵了两条半，而"区县级消费需求"是后面算蓝海红海的**唯一需求侧数据**，没有它整条链路就断。
- **AI 给的思路**：先分清"要不要为这件事写代码"——开放平台的核心障碍是**鉴权**（要注册实名 + token），这属于"人能解决、代码解决不了"的问题；而统计年鉴（成都市/四川省统计年鉴）里**同一个数就在那儿**，只是形态是 Excel。所以把问题从"怎么绕过反爬"换成"怎么把年鉴变成结构化数据"，风险从"能不能拿到"变成"解析对不对"，后者完全可控。
- **我做的决策**：接受改道，但加三条约束：① 兜底方案必须**写在文档里**（《四川统计年鉴》Excel 手工导入 ≤30 行，论文写明"官方年鉴、手工录入"），不许假装数据是自动采的；② 明确**不写 20 个市州的版式解析器**——版式一改全坏，维护成本远超收益；③ 大众点评/美团爬虫因合规风险放弃，改用高德 `biz_ext.rating` / `cost` 作消费质量代理（实测 100 条 POI 的 `raw_json` 里 `rating`、`cost` 覆盖率均 100/100）。
- **最终结果**：`region_consumption_yearly` 落库成都 2024 区县级 **20 行**（万元）、四川 2025 市州级 **21 行**（亿元×10000 转万元）；跨表自洽校验比值 **1.065**（2025 成都 11534.1 亿 ÷ 2024 区县合计 10835.3 亿），落在合理增长区间 0.9–1.2 内。`verify_s2_1b.py` 8 项检查全部通过。

### 问题 2 · 两个坑：文件名撒谎、标题行冒充表头

- **我遇到的难题**：`sichuan_2025_city_detailed.csv` 名字是 csv，实际是 xlsx（文件头 `PK\x03\x04`）——按扩展名用 `csv` 模块读，读出来全是 XML 乱码。更阴的是第二坑：成都表第 1 行是标题「表15-27 成都区(市)县社会消费品零售总额 (2024年，单位：万元)」，这一行**同时含"区(市)县"和"零售总额"**，被脚本当成表头，结果 20 行数据全部读成空值——而且**一句错都不报**。
- **AI 给的思路**：① 格式判断不信扩展名，只信**魔数**（`PK\x03\x04` + 检查 zip 里有 `xl/workbook.xml`）；② 表头判断不能"有关键字就算"，改成**给候选行打分**：这一行命中几个指标字段（总额/餐饮/商品/城镇/乡村…），命中 ≥2 个才认，标题行只能命中 1 个且是长句子，直接被筛掉。
- **我做的决策**：两个都照做，并追加一条自查手段——`--dry-run` 时打印**抽样 3 行解析结果**（地区名 + 换算后的数值），让我肉眼看一眼"锦江区 14,733,281"是不是原表那个数。这一步后来真起了作用：第一版就是靠抽样发现列全空，才回头改的表头打分。
- **最终结果**：抽样输出与年鉴原表逐字对上（锦江区 retail_total=14,733,281 万元、urban=14,733,281、rural=0——五个主城区没有乡村数据是真实情况，不是缺失）；汇总行"全 市"（中间带空格）与"四川省"被正确剔除并单独计数（21/1/20、22/1/21）。

## 阶段 S2-1d · 空间网格底盘（2026-11-15，代码完成待真机跑）

### 问题 1 · 1 km 网格铺满全省，内存一定爆

- **我遇到的难题**：要让"人口"和"灯光"能和 POI 对齐，必须把它们落到同一张网格上。但我手里是两张巨大的 GeoTIFF（灯光 534 MB、人口 878 MB）。直觉做法是"读进来再算"，可 1 km 网格若铺满四川 48.6 万 km²，就是 **约 48 万个格子**，每格再采样 + 叠路网，内存和耗时都会炸——普通笔记本上不是"慢"，是直接被杀进程。
- **AI 给的思路**：把"炸"拆成三个独立可控的点：① **区域**——先只铺成都主城区（`103.8–104.3E, 30.5–30.9N`，实测 **2160 格**），因为论文的案例分析本来就只做成都；② **硬上限**——`--max-cells 20000`，超了直接退出、不进入后续计算，绝不"先跑起来再说"；③ **读取方式**——栅格用 `rasterio` 的**窗口读取**，只读 bbox 那一小块（成都范围几千像元，几十 KB），路网用 `gpd.read_file(bbox=...)` 只读范围内要素。
- **我做的决策**：三条全采纳，并要求把"为什么只有 2160 格"写进 `grid_build_log`（bbox / 网格边长 / 网格数 / 上限 / POI 行数 / 路网要素数 / 耗时），让"我限制了范围"这件事**有账可查**，而不是嘴上说说。另外表里额外存 `area_km2`、`poi_count_amap`、`road_length_km` 三个溯源列——密度是除法算出来的，分母必须能复算。
- **最终结果**：2160 个 1 km 网格（面积 1 km² 附近，0.9886 km²，因为按中心纬度换算），`verify_s2_1d.py` 里专门有一项"网格面积合计 ≈ bbox 理论面积（偏差 <5%）"防止网格重叠或缺格；另一项要求 `poi_density_baidu` **整列为 NULL**（百度 AK 未批，一旦有值就说明有人填了假数）。

### 问题 2 · 坐标系不统一，POI 会整体偏一条街

- **我遇到的难题**：高德返回的是 **GCJ-02**（火星坐标），人口/灯光栅格和 OSM 路网是 **WGS-84**。如果直接把高德经纬度落进 WGS-84 网格，会整体偏移几百米。这种错**不报错、数值也正常**，只是所有密度都"平移一格"——最难查的那类错。
- **AI 给的思路**：在数据入口就把坐标系统一到 **WGS-84**（数据库只存一种坐标），GCJ→WGS 用公开逆向拟合公式 + round-trip 迭代修正；并且把偏移量**量化出来**写进自测输出，让"为什么必须转"变成可展示的数字，而不是一句"业界都这么干"。
- **我做的决策**：采纳"入口统一"；要求 `coord_transform.py` 自带 `__main__` 自测，打印天安门/天府广场/武侯祠三点的偏移米数与 round-trip 误差；并把"百度 BD-09 也要转"提前落成代码骨架（`baidu_adapter.py`），AK 下来只补采集、不用改结构。
- **最终结果**：实测偏移 天安门 **554.9 m**、天府广场 **360.5 m**、武侯祠 **361.1 m**，round-trip 误差 1e-6 度量级（约 0.1–0.5 m）；自测直接跑 `python datasource/coord_transform.py` 就能看到这三行。

## 阶段 S2-2 · 地域归一化

### 难题 1：要清洗的字段，本身根本不存在

- **我遇到的难题**：任务说"把 `consumption_record.city_region` 里的'未知区域'洗干净"，但我去看原始 CSV 才发现——**那张表压根没有地区列**。5 条记录的地域信息是 NULL，唯一带位置线索的是门店名（"成都春熙路店""太古里店""天府广场店""锦里店"）。
- **AI 给的思路**：先别写"字符串清洗"，先去问"这条数据里还有哪些信号能推位置"。结论是门店名。于是方案从"清洗 city_region"改成"两路归一化：字段优先，门店名兜底"，把门店名匹配定义成一次微型的地理实体识别（gazetteer matching）。
- **我做的决策**：采纳两路策略，并要求"兜底推断出的结果必须打折并标记"。理由是：字段值是实测，门店名推断是猜测，两者混在一个字段里，论文里就说不清数据质量了。
- **最终结果**：5 条全部命中（`method=landmark`，置信度 **0.81** = 0.90×0.9），`region_code` 全部回填：天府广场店→510105 青羊区、太古里店→510104 锦江区、成都春熙路店→510104、春熙路店→510104、锦里店→510107 武侯区。

### 难题 2：中文短名的模糊匹配阈值，照搬经验会翻车

- **我遇到的难题**：想用 `difflib` 兜住"武候区"这种错别字，按英文经验把阈值定 0.75，结果这条**直接判未命中**——因为 3 个字的名称只要差 1 个字，相似度就只剩 **0.667**。
- **AI 给的思路**：把"阈值"当参数而不是当常量，先自测 10 个真实样例（区县精确 / 缺后缀 / 非行政区 / 带前缀 / 错别字 / 占位词 / 空值 / 州简称 / 地标子串），看每个值落在哪个分支，再反过来定阈值。另外补了一条：**能精确补后缀就别算相似度**，"成都"应命中"成都市"而不是 0.8 相似度的模糊结果——顺序错了，`method` 会记错，报告就不可信了。
- **我做的决策**：阈值降到 **0.65**（既救回错别字又不乱认），并在匹配链里把"补后缀精确命中"插到"模糊匹配"之前；`method`/`confidence`/`note` 三个字段一起落库，让每条码都能溯源。
- **最终结果**：自测 10/10 分支判定正确（"武候区"→510107 fuzzy 0.667；"成都"→510100 exact 补后缀），清洗 5/5 命中、账本 `5 = 5 + 0` 守恒，`verify_s2_2.py` **8/8 PASS**（含幂等：再跑一次 0 条待处理）。

## 阶段 S2-1c · Olist 交易流水导入

### 难题 1：建表脚本本来"幂等"，却被我自己加的索引搞崩了

- **我遇到的难题**：为了给 Olist 打隔离标签，`consumption_record` 要补 `external_id` / `region_profile` 两列。我顺手把两列和唯一索引一起写进了 `schema_v6.sql`，结果第二次启动程序直接报错——SQLite 的 `ALTER TABLE ADD COLUMN` 不能重复执行，`initialize_schema()` 当场崩，整个桌面应用打不开。
- **AI 给的思路**：区分两件不同的事——「建表建索引」是幂等 DDL，可以放 schema 文件；「改老表结构」不是幂等操作，不能放。后者应该用 `PRAGMA table_info` 先查列在不在，不在才 `ALTER`，并且索引必须等列补上之后再建，否则报 `no such column`。
- **我做的决策**：`schema_v6.sql` 只留新表 `olist_import_log`；两列与唯一索引全部挪进 `scripts/import_olist.py` 的 `ensure_consumption_record_columns()`，并让它返回"这次补了哪几列"打印出来。这样第二次跑会输出"列已存在"，而不是崩。
- **最终结果**：连续跑三次导入，建库流程零报错；第一次补列、后两次判为已存在；重跑一次导入写入 **0** 行、唯一键命中 **112,101** 行，说明幂等生效。

### 难题 2：运费到底算不算"消费额"

- **我遇到的难题**：字段映射表里原本写的是"金额 = `price` + `freight_value`"。但细想不对：同一件商品，商家换一套包邮政策，金额就变了。
- **AI 给的思路**：把"消费额"定义成"消费者为商品本身支付的金额"，运费属于履约成本，不是消费。判断标准是：这个数字会不会因为平台运营策略而波动？会波动的不该进"消费额"。
- **我做的决策**：只取 `price`，运费不参与本项目口径，并在脚本注释与 ROADMAP 里都写明理由。同时把"为什么不含运费"写成答辩口径，因为这题一定会被问。
- **最终结果**：112,101 行、总额 **13,494,400.74**、均价 **120.38**；`verify_s2_1c.py --recheck-source` 回扫 CSV 逐行复算，源与库差值 **0.0000**，**10/10 PASS**。
